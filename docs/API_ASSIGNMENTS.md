# Назначения и выполнение работ

Описание дополнений серверной части проекта REA Auction: назначение победителя, начало работы, сдача результата, возврат и приёмка.

Документ соответствует изменениям, последовательно описанным в переписке. Итоговые файлы проекта на компьютере разработчика после ручного редактирования отдельно не проверены. Перед демонстрацией необходимо применить миграции и выполнить проверки из последнего раздела.

## 1. Что добавлено

- Модель `Assignment` — назначение работы по итогам аукциона.
- Автоматическое создание назначения в `close_auction()` при наличии победителя.
- Просмотр собственных назначений заказчиком и исполнителем.
- Начало работы только назначенным исполнителем.
- Модель `Submission` — отдельная версия сданного результата.
- Передача результата на проверку заказчику.
- Возврат с обязательным комментарием и повторная сдача.
- Приёмка результата с завершением работы.
- События начала работы, сдачи, возврата и приёмки в журнале `Event`.

Статус аукциона и статус работы разделены. После торгов аукцион остаётся `closed`, а дальнейшие действия меняют `Assignment.status`.

## 2. Модели данных

### Assignment — назначение

| Поле | Содержание |
|---|---|
| `id` | Идентификатор назначения; не обязан совпадать с номером аукциона |
| `auction` | Связь `OneToOneField` с аукционом |
| `customer` | Заказчик — владелец аукциона |
| `executor` | Назначенный исполнитель — победитель торгов |
| `price_kopecks` | Итоговая оплата по результатам аукциона |
| `due_at` | Срок выполнения из условий аукциона |
| `status` | Текущее состояние работы, первоначально `assigned` |
| `created_at` | Время создания назначения |

Ограничения базы:

- у одного аукциона не может быть двух назначений;
- цена положительная;
- заказчик и исполнитель не совпадают;
- связанные записи защищены от удаления через `PROTECT`.

Цена копируется из `Auction.payment_kopecks`, а не из собственной ставки победителя. Например, при предложениях 700, 900 и 1100 рублей исполнитель со ставкой 700 получает назначение с ценой 900 рублей.

В базе и API деньги представлены целым числом копеек: `90000` означает 900 рублей. Это исключает ошибки округления при хранении денежных сумм дробными числами.

### Submission — версия результата

| Поле | Содержание |
|---|---|
| `id` | Идентификатор версии результата |
| `assignment` | Назначение, к которому относится результат |
| `author` | Исполнитель, передавший результат |
| `text` | Текст результата, до 10000 символов |
| `version` | Последовательный номер версии внутри назначения, начиная с 1 |
| `created_at` | Время сдачи |
| `review_status` | `pending`, `returned` или `accepted` |
| `review_comment` | Комментарий заказчика; обязателен при возврате |
| `reviewed_by` | Пользователь, принявший решение; до проверки `null` |
| `reviewed_at` | Время решения; до проверки `null` |

Пара «назначение — номер версии» уникальна, номер версии не меньше 1. Предыдущие сдачи не перезаписываются. Текст из одних пробелов отклоняется. Комментарий возврата ограничен 2000 символами.

## 3. Логика работы

### Создание назначения

При завершении торгов `close_auction()`:

1. Проверяет состояние аукциона, срок и допуск участников.
2. Выбирает победителя и рассчитывает вторую цену.
3. Сохраняет итог торгов.
4. Если победитель есть, создаёт `Assignment` с заказчиком, исполнителем, ценой и сроком.
5. Записывает событие закрытия.

Все записи выполняются внутри одной `transaction.atomic`: при ошибке создания назначения результат закрытия откатывается. Повторный вызов для закрытого аукциона возвращается до создания назначения. Уникальность дополнительно защищена связью `OneToOneField`.

Без ставок аукцион закрывается без победителя и назначения. При одной ставке назначение получает её автор, цена равна бюджету. До наступления срока и при переходе в `paused` назначение не создаётся.

Для аукционов, закрытых до изменения кода, требуется отдельное заполнение старых данных: миграция заполнения либо ранее выполненный `get_or_create`. Повторный вызов `close_auction()` для старого закрытого аукциона не создаёт отсутствующее назначение.

### Состояния назначения

| Исходное состояние | Действие | Кто выполняет | Новое состояние |
|---|---|---|---|
| `assigned` — назначена | Начать работу | Исполнитель назначения | `in_progress` — в работе |
| `in_progress` — в работе | Сдать результат | Исполнитель назначения | `on_review` — на проверке |
| `on_review` — на проверке | Вернуть с комментарием | Заказчик назначения | `in_progress` — в работе |
| `on_review` — на проверке | Принять результат | Заказчик назначения | `completed` — завершена |

После возврата не нужно повторно вызывать `/start/`: работа уже находится в `in_progress`. Исполнитель отправляет новую версию через `/submit/`.

После приёмки новые сдачи, повторная приёмка, возврат и повторное начало отклоняются. Отдельных публичных методов редактирования и удаления назначений или сданных версий не добавлено.

### Проверка версии результата

Заказчик принимает решение по последней версии, определяемой максимальным номером `version`. Её исходное состояние должно быть `pending`.

При возврате версия получает `returned`, комментарий, автора и время проверки. Следующая сдача создаёт новую запись с номером на единицу больше и состоянием `pending`.

При приёмке последняя версия получает `accepted`, а назначение — `completed`. Предыдущие версии и замечания остаются в истории.

## 4. Авторизация и доступ

Используется существующая авторизация через сессии Django. Класс `Admitted` проверяет вход, активность пользователя и признак `email_verified`.

Список назначений ограничивается условием:

```python
Q(customer=request.user) | Q(executor=request.user)
```

Поэтому заказчик и исполнитель видят только назначения, стороной которых являются. Прямой запрос чужой записи возвращает `404`, не раскрывая её содержимое. Служебное право модератора само по себе доступ к чужим назначениям не даёт.

| Пользователь | Список и карточка | Начать и сдать | Принять и вернуть |
|---|---|---|---|
| Заказчик назначения | Разрешено | Запрещено, `403` | Разрешено в `on_review` |
| Исполнитель назначения | Разрешено | Разрешено в допустимом состоянии | Запрещено, `403` |
| Посторонний участник | Записи нет в списке; карточка `404` | `404` | `404` |
| Гость или недопущенный пользователь | Запрещено | Запрещено | Запрещено |

Для действий таблица предполагает корректное тело запроса. Ошибочное тело может быть отклонено с `400` до проверки предметной роли.

Изменяющие запросы требуют сессионных cookie и CSRF-токена. В формах DRF он передаётся автоматически; программный клиент отправляет его в `X-CSRFToken`. Доступ повторно проверяется в сервисных функциях.

## 5. Маршруты API

Базовый адрес локального сервера: `http://127.0.0.1:8000`.

`{id}` во всех маршрутах — идентификатор назначения, не аукциона. Тела запросов передаются в формате JSON.

| Метод | Адрес | Назначение | Успех |
|---|---|---|---|
| GET | `/api/assignments/` | Доступные текущему пользователю назначения | `200` |
| GET | `/api/assignments/{id}/` | Назначение с историей результатов | `200` |
| POST | `/api/assignments/{id}/start/` | Начать работу | `200` |
| POST | `/api/assignments/{id}/submit/` | Сдать новую версию результата | `201` |
| POST | `/api/assignments/{id}/return/` | Вернуть последнюю версию | `200` |
| POST | `/api/assignments/{id}/accept/` | Принять последнюю версию | `200` |

### Просмотр назначений

```http
GET /api/assignments/
```

Используется общая пагинация по 20 записей на страницу. Следующая страница: `?page=2`. Пример ответа:

```json
{
  "count": 1,
  "next": null,
  "previous": null,
  "results": [
    {
      "id": 1,
      "auction": 2,
      "customer": 1,
      "executor": 2,
      "price_kopecks": 90000,
      "due_at": "2026-11-05T15:00:00Z",
      "created_at": "2026-11-02T12:00:00Z",
      "status": "assigned",
      "submissions": []
    }
  ]
}
```

Значения идентификаторов и дат в примерах условные. Карточка `GET /api/assignments/1/` возвращает сам объект без оболочки пагинации. Все поля назначения доступны только для чтения через этот сериализатор; статус меняется специальными действиями.

### Начать работу

```http
POST /api/assignments/1/start/
Content-Type: application/json

{}
```

Исполнитель переводит `assigned` в `in_progress`. Ответ `200` содержит карточку назначения с обновлённым статусом. Повторный вызов возвращает `409`.

### Сдать результат

```http
POST /api/assignments/1/submit/
Content-Type: application/json

{
  "text": "Консультация проведена. Разобраны функции Python и примеры их использования."
}
```

Допустимо только для исполнителя и только из `in_progress`. Пробелы по краям удаляются; пустой текст и превышение длины отклоняются.

Ответ `201` содержит созданную версию:

```json
{
  "id": 1,
  "assignment": 1,
  "author": 2,
  "text": "Консультация проведена. Разобраны функции Python и примеры их использования.",
  "version": 1,
  "created_at": "2026-11-02T12:10:00Z",
  "review_status": "pending",
  "review_comment": "",
  "reviewed_by": null,
  "reviewed_at": null
}
```

Назначение одновременно переходит в `on_review`. Новая сдача до решения заказчика возвращает `409`.

### Вернуть на доработку

```http
POST /api/assignments/1/return/
Content-Type: application/json

{
  "comment": "Добавьте примеры использования функций"
}
```

Только заказчик, только из `on_review`. Комментарий обязателен, не может состоять из пробелов и не должен превышать 2000 символов.

Ответ `200` содержит назначение в `in_progress`. У последней версии сохраняются `review_status: returned`, комментарий, идентификатор заказчика и время решения. История доступна в массиве `submissions`.

Метод Python называется `return_result()`, поскольку `return` — служебное слово. Внешний адрес задаётся декоратором как `/return/`.

### Принять результат

```http
POST /api/assignments/1/accept/
Content-Type: application/json

{}
```

Только заказчик, только из `on_review`. Последняя версия получает `accepted`, назначение — `completed`. Ответ `200` содержит обновлённое назначение с историей. Приёмка фиксирует решение в системе, но не переводит деньги.

### Ошибки

| Код | Причина |
|---|---|
| `400` | Пустой результат, отсутствующий комментарий возврата, превышение длины или неверное тело |
| `403` | Нет допуска, неверный CSRF-токен либо сторона назначения выполняет чужое действие |
| `404` | Назначение отсутствует или недоступно текущему пользователю |
| `409` | Недопустимый статус, повтор действия, отсутствие версии для проверки или уже проверенная версия |
| `405` | Метод не поддерживается, например GET на `/start/` |

Ошибка может содержать поле `detail` или словарь ошибок входных полей. Тексты сообщений не следует использовать как стабильные машинные коды.

## 6. Транзакции и одновременные запросы

В `start_assignment()`, `submit_assignment()` и `review_assignment()` используется `@transaction.atomic` и блокировка назначения через `select_for_update()`.

На PostgreSQL действия над одним назначением выполняются последовательно: второй запрос ждёт освобождения строки и повторно проверяет статус. Например, при одновременной сдаче результата второй запрос после первой успешной сдачи увидит `on_review` и будет отклонён. При одновременных принятии и возврате применяется одно решение, второе получает конфликт.

Если запись события или другой шаг транзакции завершается ошибкой, изменения статуса и результата откатываются. Уникальность пары «назначение — версия» дополнительно защищена базой.

Сейчас локально используется SQLite: `select_for_update()` на ней не блокирует строки. Существующий режим `IMMEDIATE` последовательно выполняет записывающие транзакции, но при конкуренции возможна ошибка занятости базы. Полноценная проверка параллельных запросов требует PostgreSQL.

У действий назначения нет отдельного механизма `Idempotency-Key`: повтор успешно выполненного перехода обычно возвращает `409`. Это отличается от приёма ставок, где точный повтор ключа возвращает прежнюю ставку. При потере ответа клиенту следует перечитать карточку назначения.

## 7. Журнал событий

Используется существующая модель `Event`, связанная с аукционом.

| Событие | Когда записывается |
|---|---|
| `closed` | Закрытие аукциона; создание назначения выполняется в этой же транзакции |
| `assignment_started` | Исполнитель начал работу |
| `result_submitted` | Исполнитель сдал версию результата |
| `result_returned` | Заказчик вернул результат; причина записывается в `reason` |
| `result_accepted` | Заказчик принял результат |

В записи сохраняются автор и время. Полный текст работы хранится в `Submission`, не копируется в журнал. Решение по конкретной версии хранится в самой `Submission`; отдельного поля ссылки на версию у `Event` не добавлялось.

## 8. Где находится код

| Файл | Изменения |
|---|---|
| `auction/models.py` | `Assignment`, её статусы, `Submission` и поля проверки |
| `auction/services.py` | Создание назначения в `close_auction()`, функции `start_assignment()`, `submit_assignment()`, `review_assignment()` |
| `auction/serializers.py` | `AssignmentSerializer`, `SubmissionSerializer`, `SubmissionInput`, `AcceptInput`, `ReturnInput` |
| `auction/views.py` | `AssignmentViewSet`, ограничение списка по сторонам, действия `start`, `submit`, `accept`, `return_result` |
| `config/urls.py` | Регистрация `assignments` в существующем роутере |
| `auction/migrations/` | Миграции новых моделей и полей; номера зависят от истории вашей ветки |

`AssignmentSerializer` включает историю `submissions`. Сериализаторы действий проверяют входные данные. `submit` возвращает созданную версию, а `start`, `accept` и `return` — карточку назначения.

## 9. Применение и проверка

После сохранения изменений:

```powershell
python manage.py makemigrations auction
python manage.py migrate
python manage.py check
```

При уже созданных миграциях повторно создавать их не требуется: достаточно `migrate` и `check`. Не удаляйте прежние миграции ради перенумерации.

Команда `check` проверяет конфигурацию, но не доказывает корректность всех сценариев. После исправления ошибки отступов необходимо заново выполнить команды и проверить работу методов.

### Проверка полного цикла

1. Закрыть новый аукцион с победителем; убедиться, что создано одно назначение с верными исполнителем и ценой.
2. Повторно вызвать закрытие; проверить, что количество назначений осталось равным 1.
3. Под заказчиком и исполнителем открыть список и карточку назначения.
4. Под посторонним участником проверить отсутствие записи и ответ `404` по прямому адресу.
5. Под исполнителем вызвать `/start/`: ожидаются `200` и `in_progress`.
6. Повторить `/start/`: ожидается `409`.
7. Сдать текст через `/submit/`: ожидаются `201`, версия 1 и состояние назначения `on_review`.
8. Под заказчиком вернуть результат с комментарием: ожидается `in_progress`, версия 1 получает `returned`.
9. Под исполнителем сдать исправленный результат: создаётся версия 2, версия 1 остаётся в истории.
10. Под заказчиком принять результат: назначение получает `completed`, версия 2 — `accepted`.
11. Проверить, что новые сдачи и решения после завершения отклоняются.

Дополнительно проверить пустой текст, возврат без комментария и действия неправильной стороны назначения. Для просмотра в браузере используется существующий вход `/api-auth/login/?next=/api/`. При открытии адреса действия возможен `405`: браузер выполняет GET; действие запускается кнопкой POST с корректным телом в форме DRF.

В проекте уже есть тесты прежнего аукциона и тесты первого изменения с назначениями. Они не заменяют новые проверки `start`, `submit`, `accept` и `return`. Подтверждённых результатов автоматического запуска всего обновлённого цикла в этой версии документа нет.

## 10. Что ещё не выполнено

- PostgreSQL как фактически подключённая и проверенная база. В настройках репозитория предусмотрены переменные `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, но их наличие само по себе не означает работающего подключения.
- Конкурентные проверки новых переходов на PostgreSQL.
- Платежи, споры, загрузка файлов и автоматическая приёмка по сроку.
- Автоматическое изменение состояния назначения при просрочке или блокировке одной из сторон. Проверка допуска вызывающего пользователя не является полной обработкой блокировки всех связанных работ.

Срок `due_at` сохраняется и возвращается в API. В описанном коде он не блокирует сдачу после срока и не вызывает автоматическую приёмку.
